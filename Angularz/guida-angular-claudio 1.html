CAPITOLO 01Cos'è Angular e perché usarlo

← Torna all'indice

Angular è un framework open-source per costruire applicazioni web moderne, sviluppato e mantenuto da Google. La parola "framework" è importante: a differenza di una libreria (come React, che ti dà solo la parte di rendering), Angular ti fornisce una soluzione completa — routing, gestione delle form, HTTP client, dependency injection, testing — tutto già integrato e pensato per lavorare insieme.

1.1 La storia in due minuti

Per capire dove siamo oggi, è utile sapere da dove veniamo:

  • AngularJS (2010-2016): il primo framework, basato su JavaScript. Ha rivoluzionato il modo di scrivere SPA (Single Page Application) ma aveva grossi limiti di performance.
  • Angular 2 (2016): riscrittura completa in TypeScript. Cambia tutto: componenti invece di controller, decoratori, dependency injection nativa.
  • Angular 4-15 (2017-2022): evoluzioni progressive. Introduzione di Ivy (il nuovo motore di rendering) in Angular 9.
  • Angular 16-17 (2023): la "rinascita". Arrivano i Signals, gli standalone components, il nuovo control flow (@if, @for) e le deferrable views.
  • Angular 18-19 (2024-2025): Signals stabili, hydration completa, zoneless change detection, nuovo application builder basato su esbuild/Vite.
La versione 1 ("AngularJS") e Angular moderno (dalla 2 in poi) sono due framework completamente diversi che condividono solo il nome. Quando senti parlare di "Angular" oggi, si intende sempre Angular 2+. AngularJS è in fine vita (EOL ufficiale già passato).

1.2 Caratteristiche principali

Linguaggio: TypeScript

Angular è scritto in TypeScript ed è pensato per essere usato con TypeScript. Non è opzionale: tutti i tutorial, le API e il tooling assumono che tu lo stia usando. Questa è una buona notizia, perché TypeScript ti dà:

  • Type checking statico (errori catturati prima dell'esecuzione)
  • Autocompletamento intelligente nell'IDE
  • Refactoring sicuri (rinominare un metodo aggiorna tutti i punti d'uso)
  • Documentazione "viva" tramite i tipi stessi

Architettura a componenti

Tutto in Angular gira intorno al concetto di componente: un blocco di UI riutilizzabile che incapsula:

  • Un template (HTML che descrive cosa vedi)
  • Una classe TypeScript (logica e stato)
  • Uno o più file di stile (CSS/SCSS, scoped al componente)

Dependency Injection

Il sistema DI di Angular è uno dei più potenti al mondo. Ti permette di disaccoppiare le dipendenze e renderle facilmente sostituibili (cosa cruciale per il testing).

Reattività

Angular ha due modelli di reattività che convivono:

  1. RxJS / Observable: storico, basato sui flussi di eventi. Potente ma con curva di apprendimento ripida.
  2. Signals (dal 2023): nuovo, semplice, simile a quello di SolidJS. Sta diventando lo standard.

1.4 Quando usare Angular (e quando no)

Usalo quando…

  • Stai costruendo un'applicazione enterprise di medie/grandi dimensioni che durerà anni
  • Hai un team numeroso: la struttura rigida di Angular riduce la varianza tra sviluppatori
  • Ti servono molte feature "out-of-the-box" senza dover scegliere ed integrare 10 librerie
  • L'app ha logica complessa: form articolate, ruoli, permessi, dashboard, CRUD massicci
  • Ti interessa la stabilità a lungo termine: Angular ha cicli di rilascio prevedibili e politiche di breaking change misurate

Forse non è la scelta migliore se…

  • Devi fare un landing page o un sito statico (usa Astro, Next, o nemmeno un framework)
  • Vuoi massima flessibilità nello stack
  • Il bundle size è critico al millibyte e non puoi usare SSR

Non puoi essere produttivo in Angular senza essere a tuo agio con TypeScript. Questo capitolo non è un corso completo (per quello esiste il sito ufficiale e libri come "Programming TypeScript" di Boris Cherny), ma copre tutto ciò che ti serve sapere per scrivere Angular. 3.1 TypeScript = JavaScript + tipi

TypeScript è un superset di JavaScript: ogni file .js valido è anche un file .ts valido (rinominandolo). Aggiunge un sistema di tipi statico che viene cancellato a tempo di compilazione: a runtime non esiste più, gira normale JavaScript.

typescript
// JavaScript
function somma(a, b) {
  return a + b;
}

// TypeScript
function somma(a: number, b: number): number {
  return a + b;
}

somma("ciao", 3); // ❌ errore TS in compilazione

3.2 Tipi primitivi e collezioni

typescript
// Primitivi
let nome: string = "Claudio";
let eta: number = 30;
let attivo: boolean = true;
let nulla: null = null;
let indefinito: undefined = undefined;

// Array (due sintassi equivalenti)
let numeri: number[] = [1, 2, 3];
let nomi: Array<string> = ["Mario", "Luigi"];

// Tuple (array a lunghezza fissa con tipi specifici)
let coord: [number, number] = [10, 20];

// any: rinuncia ai tipi (usalo poco e male)
let qualunque: any = "oggi sono stringa";
qualunque = 42; // nessun errore

// unknown: come any ma DEVI verificare prima di usare
let sconosciuto: unknown = getValore();
if (typeof sconosciuto === "string") {
  console.log(sconosciuto.toUpperCase());
}
Evita any a tutti i costi. È equivalente a "spegni il type checker per questa variabile". Quando non sai un tipo, usa unknown: ti costringe a verificarlo prima di usarlo.

3.3 Interfacce e Type Aliases

Sono i due modi per descrivere la "forma" di un oggetto. Per Angular si usano entrambi.

typescript
// Interface (preferita per oggetti estensibili)
interface User {
  id: number;
  nome: string;
  email: string;
  eta?: number; // opzionale
  readonly creato: Date; // solo lettura
}

// Estensione
interface Admin extends User {
  permessi: string[];
}

// Type alias (preferito per union, intersection, primitivi)
type ID = string | number;
type Status = "attivo" | "sospeso" | "cancellato";
type UserConPermessi = User & { permessi: string[] };
Regola pratica: usa interface per descrivere oggetti che potrebbero essere estesi (es. modelli di dominio); usa type per union, intersection e tipi più "funzionali". In pratica si usano in modo intercambiabile e va benissimo.

3.4 Classi

Angular usa molto le classi (i componenti, i servizi, le pipe, le direttive sono tutti classi).

typescript
class Persona {
  // Modificatori di accesso
  public nome: string;       // default, accessibile da fuori
  private _eta: number;       // solo dentro la classe
  protected id: number;      // classe + sottoclassi
  readonly dataNascita: Date; // immutabile dopo costruzione

  constructor(nome: string, eta: number) {
    this.nome = nome;
    this._eta = eta;
    this.id = Math.random();
    this.dataNascita = new Date();
  }

  // Getter/Setter
  get eta(): number { return this._eta; }
  set eta(valore: number) {
    if (valore < 0) throw new Error("Età invalida");
    this._eta = valore;
  }

  // Metodo
  saluta(): string {
    return `Ciao, sono ${this.nome}`;
  }
}

// Sintassi compatta del costruttore (parameter properties)
class PersonaCompatta {
  constructor(
    public nome: string,
    private eta: number
  ) {} // equivalente al codice sopra ma in 4 righe
}

3.5 Generics

I generics sono "tipi parametrici": permettono di scrivere funzioni e classi che lavorano con tipi diversi mantenendo la sicurezza dei tipi.

typescript
// Funzione generica
function primo<T>(arr: T[]): T | undefined {
  return arr[0];
}

const n = primo([1, 2, 3]);        // n: number | undefined
const s = primo(["a", "b"]);      // s: string | undefined

// Classe generica (es. il response wrapper di un'API)
class ApiResponse<T> {
  constructor(
    public data: T,
    public status: number
  ) {}
}

const users: ApiResponse<User[]> = new ApiResponse([], 200);

// Constraints (T deve avere certe proprietà)
function stampaNome<T extends { nome: string }>(obj: T) {
  console.log(obj.nome);
}

3.6 Decoratori

I decoratori sono fondamentali in Angular: @Component, @Injectable, @Input, ecc. sono tutti decoratori. Sono funzioni speciali che "decorano" una classe (o un suo membro) aggiungendo metadata.

typescript
// Esempio di decoratore custom (a scopo illustrativo)
function Loggable(target: any) {
  console.log(`Classe definita: ${target.name}`);
}

@Loggable
class Servizio { ... }

// In Angular: i decoratori marcano una classe come
// componente/servizio/direttiva/pipe. Esempio reale:
@Component({
  selector: 'app-hello',
  template: '<h1>Ciao!</h1>'

3.7 Type narrowing

Quando hai una union type, TS "restringe" il tipo nei rami in cui sa cosa hai:

typescript
function stampa(valore: string | number) {
  if (typeof valore === "string") {
    console.log(valore.toUpperCase()); // qui valore: string
  } else {
    console.log(valore.toFixed(2));   // qui valore: number
  }
}

// Discriminated unions (uno dei pattern più potenti di TS)
type Stato =
  | { kind: "loading" }
  | { kind: "success"; data: User[] }
  | { kind: "error"; messaggio: string };

function render(s: Stato) {
  switch (s.kind) {
    case "loading": return "caricamento...";
    case "success": return `${s.data.length} utenti`; // data accessibile
    case "error":   return `Errore: ${s.messaggio}`;
  }
}

4.5 Servizio per la gestione delle todo

typescript — services/todo.service.ts
import { Injectable, signal, computed } from '@angular/core';
import { Todo } from '../models/todo';

@Injectable({ providedIn: 'root' })
export class TodoService {
  // Stato privato (signal writable)
  private readonly _todos = signal<Todo[]>([]);

  // API pubblica readonly
  readonly todos = this._todos.asReadonly();
  readonly completate = computed(() =>
    this._todos().filter(t => t.completata).length
  );

  aggiungi(testo: string): void {
    const nuova: Todo = {
      id: Date.now(),
      testo,
      completata: false,
      creataIl: new Date()
    };
    this._todos.update(arr => [...arr, nuova]);
  }

  toggle(id: number): void {
    this._todos.update(arr =>
      arr.map(t => t.id === id ? { ...t, completata: !t.completata } : t)
    );
  }

  rimuovi(id: number): void {
    this._todos.update(arr => arr.filter(t => t.id !== id));
  }
}
Pattern fondamentale: signal privato + alias readonly pubblico. I componenti possono leggere ma non modificare lo stato direttamente; tutte le mutazioni passano dai metodi del servizio. Questo è uno dei pattern più importanti che imparerai.

4.6 Componente che usa il servizio

typescript — pages/todo-list.component.ts
import { Component, inject } from '@angular/core';
import { FormsModule } from '@angular/forms';
import { TodoService } from '../services/todo.service';

@Component({
  selector: 'app-todo-list',
  imports: [FormsModule],
  template: `

      <input
        [(ngModel)]="testo"
        (keyup.enter)="aggiungi()"

  2. [(ngModel)] è il "two-way binding" sul testo dell'input
  3. @if/@for è il nuovo control flow nativo (capitolo 8)
  4. track todo.id dice ad Angular come identificare gli elementi (per ottimizzare il rendering)
  5. {{ ... }} è l'interpolazione: stampa il valore

  • I provider funzionali (provideRouter, provideHttpClient) sostituiscono i vecchi NgModule
  • Il pattern signal privato + readonly pubblico è la base per gestire lo stato

← Torna all'indice

Ora che hai costruito qualcosa, è il momento di fermarsi e capire come è organizzata un'applicazione Angular. Saperlo ti permette di prendere decisioni di architettura solide invece di copiare e incollare a caso.

5.1 I building block

5.2 Standalone vs NgModule

Storicamente Angular usava i NgModule: contenitori che dichiaravano un set di componenti/direttive/pipe e li esportavano. Era complesso, verboso, fonte di errori "X is not a known element".

Da Angular 14 sono arrivati i componenti standalone; da Angular 17 sono il default. Un componente standalone importa direttamente quello che usa, senza bisogno di moduli intermedi.

typescript
// Vecchio mondo (NgModule)
@NgModule({
  declarations: [MyComponent],
  imports: [CommonModule, FormsModule, MatButtonModule],
  exports: [MyComponent]
})
export class MyModule {}

// Nuovo mondo (standalone) — molto più semplice
@Component({
  selector: 'app-my',
  imports: [FormsModule, MatButton], // importa solo qui
  template: `...`
})
export class MyComponent {}
Se trovi tutorial vecchi (Angular 14 e precedenti) che parlano di app.module.ts, di declarations, di BrowserModule, ecc.: è materiale obsoleto. Salta o cerca la versione aggiornata. La sintassi che impari oggi (standalone) è il futuro.

5.3 Il flusso di rendering

  1. Bootstrap: main.ts avvia l'app con bootstrapApplication(AppComponent, ...)
  2. Albero dei componenti: Angular costruisce l'albero a partire da AppComponent, risolvendo via via tutti i componenti figli
  3. Iniezione delle dipendenze: per ogni componente, Angular istanzia o riusa i servizi richiesti
  4. Rendering: i template vengono compilati in funzioni che generano HTML reale
  5. Change detection: ad ogni evento (click, timer, HTTP response) Angular controlla cosa è cambiato e aggiorna il DOM

5.4 Struttura cartelle consigliata

Non c'è "uno modo corretto", ma ci sono convenzioni che funzionano. Per app medio-grandi:

5.5 Dependency Injection: il cuore di Angular

DI è il meccanismo per cui un componente chiede ciò che gli serve invece di crearlo da sé. Vantaggi:

  • Disaccoppiamento: il componente non sa chi crea il servizio
  • Testabilità: nei test puoi sostituire un servizio con un mock
  • Singleton condivisi: lo stesso servizio è condiviso tra tutti i componenti che lo usano
typescript
// Il servizio si "registra" da solo nel root injector
@Injectable({ providedIn: 'root' })
export class AuthService { ... }

// Il componente lo "richiede"
export class LoginComponent {
  private auth = inject(AuthService);
}
  • Componente, Servizio, Direttiva, Pipe sono i 4 building block principali
  • Da Angular 17, tutto è standalone — niente NgModule

  • La Dependency Injection è il glue di Angular

6.3 Input — passare dati al componente

Gli input sono il modo in cui un componente padre passa dati al figlio. Da Angular 17.1 esiste la nuova API basata sui signal (input()) — è il modo che dovresti imparare.

import { Component, Input } from '@angular/core';

  @Input({ required: true }) eta!: number;

typescript — nuova API (signal-based)
import { Component, input } from '@angular/core';

@Component({ selector: 'app-greeting', template: `Ciao, {{ nome() }}!` })
export class GreetingComponent {
  readonly nome = input<string>('');                // optional con default
  readonly eta  = input.required<number>();        // required
  readonly tipo = input('', {
    alias: 'ruolo',
    transform: (v: string) => v.toUpperCase()
  });
}

Uso dal template del padre:

html
<app-greeting nome="Claudio" [eta]="30" ruolo="admin" />

7.1 Interpolazione

La forma più semplice di binding: stampa un valore nel testo HTML.

html

CAPITOLO 08Control flow nativo (@if, @for, @switch)

← Torna all'indice

Una delle novità più amate di Angular 17 è il nuovo control flow integrato nel linguaggio dei template, che sostituisce le vecchie direttive *ngIf, *ngFor, *ngSwitch. È più veloce a runtime, ha una migliore type inference e una sintassi molto più leggibile.

8.1 @if / @else if / @else

html
@if (utente()) {
  <p>Benvenuto, {{ utente()!.nome }}</p>
} @else if (caricamento()) {
  <p>Caricamento...</p>
} @else {
  <p>Effettua il login.</p>
}

Pattern utilissimo: il "let-binding" che evita controlli null ridondanti:

html
@if (utente(); as u) {
  <p>Ciao {{ u.nome }} ({{ u.email }})</p>
}

8.2 @for

Il nuovo @for richiede obbligatoriamente un track. Questo è una scelta deliberata: senza track Angular non sa identificare gli elementi e fa rendering inefficiente.

html
@for (todo of todos(); track todo.id) {
  <li>{{ todo.testo }}</li>
} @empty {
  <li>Nessuna attività.</li>
}

Variabili contestuali disponibili:

VariabileSignificato
$indexindice corrente (0-based)
$countnumero totale di elementi
$firsttrue se primo elemento
$lasttrue se ultimo
$even / $oddtrue se indice pari/dispari
html
@for (item of lista(); track item.id; let i = $index, last = $last) {
  <div [class.ultimo]="last">{{ i + 1 }}. {{ item.nome }}</div>
}

8.3 @switch

html
@switch (stato()) {
  @case ('loading') { <app-spinner /> }
  @case ('success') { <app-tabella [data]="dati()" /> }
  @case ('error')   { <app-errore [msg]="errore()" /> }
  @default          { <p>Stato sconosciuto.</p> }
}

8.4 @defer (deferrable views)

Le deferrable views sono una delle feature più innovative di Angular 17+. Permettono di caricare in modo lazy un blocco del template (e tutti i suoi imports!) in base a un trigger.

html
@defer (on viewport) {
  <app-grafico-pesante [data]="metriche()" />
} @loading (after 100ms; minimum 1s) {
  <app-skeleton />
} @error {
  <p>Errore caricamento.</p>
} @placeholder (minimum 500ms) {
  <p>Scorri per vedere il grafico</p>
}

Trigger disponibili:

TriggerQuando si attiva
on idlequando il browser è inattivo (default)
on viewportquando il blocco entra nel viewport
on interactional primo click/keypress dentro
on hoveral primo hover dentro
on immediatesubito dopo il rendering iniziale
on timer(2s)dopo un timer

Le deferrable views si combinano con il code splitting automatico: i componenti referenziati dentro @defer finiscono in chunk separati, scaricati on-demand. È il modo più semplice di ottimizzare le performance.

8.5 Migrazione dalle vecchie direttive

9.3 Direttive strutturali custom

Una direttiva strutturale aggiunge/rimuove elementi dal DOM. La sintassi *nome è zucchero per <ng-template>.

typescript — esempio: appUnless (opposto di if)
import { Directive, Input, TemplateRef, ViewContainerRef, inject } from '@angular/core';

@Directive({ selector: '[appUnless]' })
export class UnlessDirective {
  private tpl = inject<TemplateRef<unknown>>(TemplateRef);
  private vcr = inject(ViewContainerRef);
  private isShown = false;

  @Input() set appUnless(condizione: boolean) {
    if (!condizione && !this.isShown) {
      this.vcr.createEmbeddedView(this.tpl);
      this.isShown = true;
    } else if (condizione && this.isShown) {
      this.vcr.clear();
      this.isShown = false;
    }
  }
}
Oggi quasi nessuno scrive direttive strutturali custom: con @if/@for/@defer il bisogno è quasi sparito. Ma capirne il meccanismo è utile per debug e per leggere codice legacy.
  • Le direttive sono di tre tipi: componente, attributo, strutturali
  • Le strutturali (*ngIf, *ngFor) sono in deprecazione: usa il control flow
  • Usa NgOptimizedImage per le immagini
  • Direttive di attributo custom con @HostListener e ElementRef

10.3 Pure vs impure pipes

Per default le pipe sono pure: vengono eseguite solo quando l'input cambia per riferimento. Una pipe impure viene eseguita ad ogni change detection (lentissima — usala solo se sai cosa stai facendo):

typescript

export class FiltraPipe implements PipeTransform { ... }
Evita le pipe impure. Se devi filtrare un array, fallo nel componente con un computed() o un signal: è più efficiente e più chiaro.

  • Tieni le pipe pure; per logica di filtro usa computed()

CAPITOLO 11Signals — il nuovo paradigma reattivo

← Torna all'indice

I Signals sono la novità più importante di Angular degli ultimi cinque anni. Introdotti in v16 (developer preview), stabilizzati in v17, sono diventati la base della reattività moderna. Capirli bene è il singolo investimento di tempo che renderà di più nella tua carriera Angular.

11.1 Cos'è un signal

Un signal è una scatola con un valore osservabile: chi legge il valore "si registra" automaticamente, e quando il valore cambia tutti i lettori vengono notificati. È un'idea presa da SolidJS, MobX, Vue e Knockout — vecchia di anni nel resto dell'ecosistema, finalmente arrivata in Angular.

typescript
import { signal } from '@angular/core';

const count = signal(0);

// Lettura: chiamando come funzione
console.log(count()); // 0

// Scrittura completa
count.set(5);
console.log(count()); // 5

// Update basato sul valore precedente
count.update(v => v + 1);
console.log(count()); // 6

11.2 Computed signals

Un computed è un signal derivato da altri signal. Si ricalcola automaticamente solo quando una sua dipendenza cambia. È memoizzato: se nessuna dipendenza è cambiata, ritorna il valore in cache.

typescript
import { signal, computed } from '@angular/core';

const nome  = signal('Mario');
const cogn  = signal('Rossi');
const nomeCompleto = computed(() => `${nome()} ${cogn()}`);

console.log(nomeCompleto()); // "Mario Rossi"
nome.set('Luigi');
console.log(nomeCompleto()); // "Luigi Rossi" (ricalcolato)
I computed sono read-only: non puoi fare .set() o .update(). Per cambiare il valore devi cambiare i signal di partenza.

11.3 Effect

Gli effect eseguono codice come side-effect al cambio di un signal. Tipico uso: salvare in localStorage, fare logging, sincronizzare con qualcosa fuori da Angular.

typescript
import { Component, signal, effect } from '@angular/core';

@Component({ ... })
export class SettingsComponent {
  tema = signal<'light' | 'dark'>('light');

  constructor() {
    effect(() => {
      const t = this.tema();
      document.body.dataset.theme = t;
      localStorage.setItem('tema', t);
    });
  }
}
Non usare effect per derivare valori. Se vuoi un valore calcolato, usa computed(). Gli effect sono per side-effect veri (DOM manuale, localStorage, log, ecc.). Una regola: se l'unico contenuto dell'effect è una set di un altro signal, stai sbagliando.

11.5 Esempio realistico: filtro su lista

typescript
@Component({ ... })
export class ProdottiComponent {
  private _all = signal<Prodotto[]>([]);
  readonly filtro = signal('');
  readonly minPrezzo = signal(0);

  // Computed: si aggiorna solo se _all, filtro o minPrezzo cambiano
  readonly visibili = computed(() => {
    const testo = this.filtro().toLowerCase();
    const min = this.minPrezzo();
    return this._all()
      .filter(p => p.nome.toLowerCase().includes(testo))
      .filter(p => p.prezzo >= min);
  });

  readonly totale = computed(() =>
    this.visibili().reduce((s, p) => s + p.prezzo, 0)
  );
}

CAPITOLO 12RxJS e Observable

← Torna all'indice

RxJS è la libreria di reactive programming su cui Angular è nato. Anche se i Signal coprono molti casi d'uso, RxJS rimane insostituibile per: HTTP, eventi DOM complessi, debounce di input, polling, retry, websocket, e qualsiasi cosa coinvolga timing/composizione di stream asincroni.

12.1 Cos'è un Observable

Un Observable è una "promessa che può emettere più valori nel tempo". Un Observable rappresenta un flusso di valori a cui ti puoi abbonare.

typescript
import { Observable } from 'rxjs';

const stream$ = new Observable<number>(observer => {
  observer.next(1);
  observer.next(2);
  setTimeout(() => {
    observer.next(3);
    observer.complete();
  }, 1000);
});

stream$.subscribe({
  next: v => console.log(v),         // 1, 2, poi dopo 1s: 3
  error: e => console.error(e),
  complete: () => console.log('fine')
});
Convenzione: i nomi delle variabili Observable terminano con $ (sigaro/dollaro). Es. users$, filtro$. Aiuta a riconoscerle al volo.

12.2 Operatori essenziali

RxJS ha centinaia di operatori. Quelli che userai il 90% del tempo sono questi 15:

OperatoreCosa fa

take(n)Prende i primi N valori e completa
takeUntil($)Emette finché un altro stream non emette
debounceTime(ms)Aspetta X ms di silenzio prima di emettere (perfetto per search)

12.3 La differenza tra switchMap, mergeMap, concatMap, exhaustMap

Capirla bene risparmia bug devastanti. Tutti e quattro prendono un valore e lanciano un nuovo Observable basato su esso. Differiscono nella strategia quando arriva un nuovo valore prima che il precedente Observable interno sia completato:

OperatoreStrategiaQuando usarlo

mergeMapEsegue entrambi in paralleloUpload multiplo, eventi indipendenti
concatMapMette in coda, esegue uno alla voltaSave/update sequenziali
exhaustMapIgnora il nuovo se il vecchio è ancora attivoLogin (evita doppi click)

12.4 Esempio classico: search live

typescript
import { Component, inject } from '@angular/core';
import { FormControl, ReactiveFormsModule } from '@angular/forms';
import { HttpClient } from '@angular/common/http';
import { debounceTime, distinctUntilChanged, switchMap, filter } from 'rxjs';
import { toSignal } from '@angular/core/rxjs-interop';

@Component({
  imports: [ReactiveFormsModule],
  template: `
    <input [formControl]="search" placeholder="Cerca..." />
    @for (r of risultati(); track r.id) {
      <li>{{ r.nome }}</li>
    }
  `
})
export class SearchComponent {
  private http = inject(HttpClient);
  readonly search = new FormControl('', { nonNullable: true });

  readonly risultati = toSignal(
    this.search.valueChanges.pipe(
      debounceTime(300),                      // aspetta 300ms di "silenzio"
      distinctUntilChanged(),                  // salta se il valore è uguale
      filter(t => t.length >= 2),              // almeno 2 caratteri
      switchMap(t =>                            // cancella la richiesta vecchia
        this.http.get<Risultato[]>(`/api/cerca?q=${t}`)
      )
    ),
    { initialValue: [] }
  );
}

I Subject sono Observable e Observer al tempo stesso. Servono quando devi emettere manualmente.

Storico: BehaviorSubject era il modo standard per gestire stato in Angular. Oggi nelle nuove app si usa signal(): stessa semantica ma senza la macchineria RxJS.

12.6 Il problema del memory leak

Se ti subscrivi a un Observable e non ti unsubscribi, hai un memory leak. È il bug più comune in Angular tradizionale.

typescript
// ❌ MALE: leak garantito
export class MyComp implements OnInit {
  ngOnInit() {
    interval(1000).subscribe(v => console.log(v));
  }
}

// ✅ BENE: con takeUntilDestroyed
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';

export class MyComp {
  constructor() {
    interval(1000)
      .pipe(takeUntilDestroyed())
      .subscribe(v => console.log(v));
  }
}

// ✅ ALTERNATIVA: usa async pipe nel template e zero subscribe manuale
  • RxJS gestisce flussi asincroni complessi (HTTP, eventi, timer)
  • Operatori chiave: map, filter, switchMap, debounceTime, catchError
  • Differenze switchMap/mergeMap/concatMap/exhaustMap: studiale a memoria
  • Per gestire le subscribe: takeUntilDestroyed() o async pipe
  • toSignal() e toObservable() sono il ponte tra Signal e RxJS

CAPITOLO 13Change detection

← Torna all'indice

La change detection è il meccanismo per cui Angular sa quando aggiornare il DOM in risposta a un cambio di stato. Capirla è la differenza tra un'app Angular veloce e una che si trascina.

13.1 Come funziona Zone.js (modello classico)

Storicamente, Angular usa zone.js: una libreria che fa "monkey patch" su tutte le API browser asincrone (setTimeout, eventi DOM, fetch, ecc.). Ogni volta che una di queste si conclude, Angular esegue change detection sull'intera app.

Questo significa che ogni click, anche su un pulsante che non cambia nulla, scatena un controllo di tutta l'app. In app grandi è un problema di performance.

13.2 OnPush change detection

La strategia OnPush dice ad Angular: "controlla questo componente solo se uno dei suoi input cambia per riferimento, o se emette un evento dal template, o se un Observable nel template emette via async pipe, o se un signal usato cambia".

typescript
import { Component, ChangeDetectionStrategy } from '@angular/core';

@Component({
  selector: 'app-card',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `...`
})
export class CardComponent { ... }
Imposta OnPush come default in angular.json sotto schematics per i nuovi componenti. È un'ottimizzazione "free" che disciplina anche il modo in cui scrivi i componenti (immutabilità, stream, signal).

13.3 Zoneless change detection

Da Angular 18 esiste l'opzione zoneless: l'app gira senza zone.js. Significa: niente monkey-patching, bundle più piccolo, e change detection scatenata solo da Signal, async pipe e eventi del template.

typescript — app.config.ts
import { provideExperimentalZonelessChangeDetection } from '@angular/core';

export const appConfig: ApplicationConfig = {
  providers: [
    provideExperimentalZonelessChangeDetection(),
    ...
  ]
};

Per andare zoneless devi:

  • Usare Signal (o Observable + async pipe) per tutto lo stato
  • Eliminare setTimeout e setInterval diretti dai componenti (preferisci RxJS o effect)
  • Verificare che le librerie terze parti siano compatibili
Il futuro di Angular è zoneless. Le app nuove dovrebbero adottarlo dal day 1; le esistenti possono migrare gradualmente.

13.4 Trigger manuali

In casi rari hai bisogno di triggerare change detection a mano:

typescript
import { ChangeDetectorRef, inject } from '@angular/core';

export class MyComp {
  private cdr = inject(ChangeDetectorRef);

  aggiorna() {
    // fai qualcosa fuori dalla zona
    this.cdr.markForCheck();   // segna come "da controllare"
    // oppure
    this.cdr.detectChanges(); // forza ora
  }
}
  • Change detection = "decidere cosa rerenderizzare"
  • OnPush + immutabilità = base per app performanti
  • Signal trigger granulari, lavorano benissimo con OnPush
  • Zoneless è il futuro: usalo nei progetti nuovi

CAPITOLO 14Servizi

← Torna all'indice

I servizi sono le classi dove vive la logica che non riguarda direttamente la UI: chiamate HTTP, manipolazione di stato, business logic, autenticazione, log, ecc. La regola: i componenti orchestrano, i servizi fanno il lavoro.

14.1 Definire un servizio

typescript
import { Injectable } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class Logger {
  log(messaggio: string): void {
    console.log(`[${new Date().toISOString()}] ${messaggio}`);
  }
}

providedIn: 'root' significa: c'è una singola istanza per tutta l'app, creata pigramente al primo uso (tree-shakable: se nessuno la inietta, non finisce nel bundle).

14.2 Tipi di scope

providedInEffetto
'root'Singleton globale (90% dei casi)
'platform'Singleton per più app sulla stessa pagina (raro)
'any'Una nuova istanza per ogni "lazy" injector
(in providers del componente)Una istanza per ogni istanza del componente

14.3 Esempio: AuthService

typescript
import { Injectable, signal, computed, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Router } from '@angular/router';

@Injectable({ providedIn: 'root' })
export class AuthService {
  private http = inject(HttpClient);
  private router = inject(Router);

  private _user = signal<User | null>(null);
  readonly user        = this._user.asReadonly();
  readonly isLoggedIn  = computed(() => this._user() !== null);
  readonly isAdmin     = computed(() => this._user()?.ruolo === 'admin');

  async login(email: string, password: string) {
    const u = await firstValueFrom(
      this.http.post<User>('/api/login', { email, password })
    );
    this._user.set(u);
    this.router.navigate(['/dashboard']);
  }

  logout(): void {
    this._user.set(null);
    this.router.navigate(['/login']);
  }
}

14.4 Quando creare un servizio

  • Quando logica simile è duplicata in più componenti
  • Quando un componente diventa "troppo grande" e mischia UI e logica
  • Quando lo stato deve sopravvivere al ciclo di vita del componente
  • Quando vuoi testare la logica isolatamente
  • I servizi sono classi @Injectable({ providedIn: 'root' })
  • Sono singleton di default — perfetti per stato condiviso
  • Usali per: HTTP, stato, business logic, log, autenticazione
  • I componenti dovrebbero essere "magri": orchestrano, non lavorano

CAPITOLO 15Dependency Injection con inject()

← Torna all'indice

Il sistema DI di Angular merita un capitolo a sé. Non è solo "passare dipendenze al costruttore": è un'architettura gerarchica di injector con regole precise.

15.1 inject() vs costruttore

Storicamente le dipendenze si dichiaravano nel costruttore:

typescript — vecchio modo
export class MyComp {
  constructor(
    private http: HttpClient,
    private router: Router,
    private auth: AuthService
  ) {}
}

Da Angular 14 è arrivata la funzione inject(), che è più elegante e flessibile:

typescript — nuovo modo
import { inject } from '@angular/core';

export class MyComp {
  private http   = inject(HttpClient);
  private router = inject(Router);
  private auth   = inject(AuthService);
}

Vantaggi di inject():

  • Niente boilerplate del costruttore
  • Funziona dentro funzioni (factories, guard, interceptor, resolver)
  • Type narrowing migliore
  • Permette pattern di composizione interessanti
inject() funziona solo in "injection context": dentro costruttori, factories, e gli inizializzatori di campo. Fuori da questi (es. dentro un metodo arbitrario) ti dà errore. Per recuperare il contesto si può usare runInInjectionContext ma raramente serve.

15.2 Provider personalizzati

Puoi sostituire o configurare ciò che viene iniettato:

typescript
// useClass: sostituisci con un'altra classe
{ provide: Logger, useClass: ConsoleLogger }

// useValue: usa un valore costante
{ provide: API_URL, useValue: 'https://api.example.com' }

// useFactory: crea con una funzione
{
  provide: HttpClient,
  useFactory: () => new CustomHttpClient(inject(API_URL)),
}

// useExisting: alias di un altro provider
{ provide: NewLogger, useExisting: Logger }

15.3 InjectionToken

Per iniettare valori (non classi), si usano i token:

typescript
import { InjectionToken } from '@angular/core';

export const API_URL = new InjectionToken<string>('API_URL');

// Provider
providers: [{ provide: API_URL, useValue: 'https://api.example.com' }]

// Uso
private apiUrl = inject(API_URL);

15.4 Gerarchia degli injector

Ogni componente ha un suo injector. Quando chiedi un servizio, Angular sale l'albero finché non lo trova:

RootInjector (livello applicazione)
└─ AppComponent
   └─ DashboardComponent
      └─ UserListComponent
         └─ UserItemComponent

Se un servizio è registrato in UserListComponent (via providers: [...] nel decoratore), tutti gli UserItemComponent figli ne ricevono la stessa istanza, ma il resto dell'app ne riceve un'altra.

15.5 Il pattern "feature service"

Quando vuoi che ogni feature/pagina abbia il suo stato isolato:

typescript
@Injectable() // niente providedIn
export class UsersFeatureService {
  readonly users = signal<User[]>([]);
  ...
}

@Component({
  selector: 'app-users-page',
  providers: [UsersFeatureService], // scope di pagina
  template: `...`
})
export class UsersPageComponent {
  protected svc = inject(UsersFeatureService);
}

Quando navighi via dalla pagina, l'istanza viene distrutta. Quando torni, ne nasce una nuova. Pattern utilissimo per isolare lo stato delle feature.

  • inject() è il modo moderno di ricevere dipendenze
  • I provider possono usare useClass, useValue, useFactory, useExisting
  • Gli InjectionToken permettono di iniettare valori costanti
  • Gli injector sono gerarchici: capirli ti permette di gestire scope avanzati

CAPITOLO 18Reactive forms

← Torna all'indice

I reactive forms hanno il modello nel codice TypeScript: testabili, type-safe, perfetti per logica complessa. Sono lo standard de-facto per app medio-grandi.

18.1 FormControl, FormGroup, FormArray

I tre mattoni:

  • FormControl: un singolo campo
  • FormGroup: un gruppo di controlli (un oggetto form)
  • FormArray: un array di controlli (lista dinamica)
typescript
import { Component, inject } from '@angular/core';
import { FormBuilder, ReactiveFormsModule, Validators } from '@angular/forms';

@Component({
  imports: [ReactiveFormsModule],
  templateUrl: './registrazione.component.html'
})
export class RegistrazioneComponent {
  private fb = inject(FormBuilder);

  readonly form = this.fb.nonNullable.group({
    nome: ['', [Validators.required, Validators.minLength(2)]],
    email: ['', [Validators.required, Validators.email]],
    eta: [18, [Validators.min(0), Validators.max(120)]],
    indirizzo: this.fb.nonNullable.group({
      via: ['', Validators.required],
      citta: ['', Validators.required]
    }),
    interessi: this.fb.array([])
  });

  submit() {
    if (this.form.invalid) {
      this.form.markAllAsTouched();
      return;
    }
    const dati = this.form.getRawValue(); // type-safe!
    console.log(dati);
  }
}
html
<form [formGroup]="form" (ngSubmit)="submit()">

    <input formControlName="via" />
    <input formControlName="citta" />

import { AbstractControl, ValidationErrors, ValidatorFn } from '@angular/forms';

export const codiceFiscaleValidator: ValidatorFn = (
  ctrl: AbstractControl

  const v: string = ctrl.value ?? '';
  if (!v) return null; // vuoto = lascia fare a "required"
  const regex = /^[A-Z]{6}\d{2}[A-Z]\d{2}[A-Z]\d{3}[A-Z]$/;

19.4 Validatore async

Tipico caso: verificare se un username è già preso interrogando il backend.

typescript
import { AsyncValidatorFn } from '@angular/forms';
import { of, debounceTime, switchMap, map, catchError } from 'rxjs';

export function usernameDisponibileValidator(api: UserApi): AsyncValidatorFn {
  return (ctrl) => {
    if (!ctrl.value) return of(null);
    return ctrl.valueChanges.pipe(
      debounceTime(400),
      switchMap(v => api.esiste(v)),
      map(esiste => (esiste ? { usernamePreso: true } : null)),
      catchError(() => of(null)),
      first()
    );
  };
}

CAPITOLO 24Interceptors funzionali

← Torna all'indice

Gli interceptor intercettano tutte le richieste HTTP. Casi tipici: aggiungere il token di autenticazione, mostrare un loader globale, gestire errori in modo centralizzato, retry automatici, log.

24.1 Interceptor base: aggiungere il token

typescript — interceptors/auth.interceptor.ts
import { HttpInterceptorFn } from '@angular/common/http';
import { inject } from '@angular/core';
import { AuthService } from '../core/auth.service';

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).token();
  if (!token) return next(req);

  const req2 = req.clone({
    setHeaders: { Authorization: `Bearer ${token}` }
  });
  return next(req2);
};
typescript — registrazione
provideHttpClient(withInterceptors([authInterceptor, errorInterceptor, loadingInterceptor]))

24.2 Error interceptor

typescript
import { HttpErrorResponse, HttpInterceptorFn } from '@angular/common/http';
import { catchError, throwError } from 'rxjs';

export const errorInterceptor: HttpInterceptorFn = (req, next) => {
  const toast = inject(ToastService);
  const auth  = inject(AuthService);

  return next(req).pipe(
    catchError((err: HttpErrorResponse) => {
      switch (err.status) {
        case 401: auth.logout(); break;
        case 403: toast.errore('Non autorizzato'); break;
        case 0:   toast.errore('Sei offline?'); break;
        case 500: toast.errore('Errore server'); break;
      }
      return throwError(() => err);
    })
  );
};

24.3 Loading interceptor

typescript
export const loadingInterceptor: HttpInterceptorFn = (req, next) => {
  const loader = inject(LoaderService);
  loader.show();
  return next(req).pipe(
    finalize(() => loader.hide())
  );
};

24.4 Ordine di esecuzione

Gli interceptor si eseguono nell'ordine in cui li passi all'array. Per la response, l'ordine è inverso. Tipicamente: auth → log → error → loading.
  • Gli interceptor sono funzioni registrate con withInterceptors([...])
  • Pattern essenziali: auth (token), errori, loading
  • req.clone({...}) per modificare la richiesta (le HttpRequest sono immutabili)
  • Per la response, next(req).pipe(...)

CAPITOLO 26State management

← Torna all'indice

Il problema: lo stato dell'app cresce — utente loggato, carrello, preferenze, cache di liste, notifiche. Senza un approccio chiaro, finisce sparso ovunque e diventa un incubo.

26.1 La scala delle complessità

ApproccioQuando usarlo
Signal nei componentiStato locale di un componente
Servizio + signalStato condiviso tra pochi componenti — la scelta giusta nel 70% dei casi
Signal Store (NgRx)Stato condiviso strutturato con regole, perfetto per feature complesse
NgRx classicoApp enterprise con time-travel debugging, eventi rintracciabili, audit

Non saltare al livello sopra prematuramente. NgRx introduce molto boilerplate. Per un'app medio-piccola, un servizio con signal è più che sufficiente e si scrive in un decimo del tempo.

26.2 Pattern "service with signals"

Lo schema base che funziona benissimo per il 70% dei casi:

typescript
@Injectable({ providedIn: 'root' })
export class CarrelloStore {
  private _items = signal<Item[]>([]);

  // === API pubblica readonly ===
  readonly items   = this._items.asReadonly();
  readonly count   = computed(() => this._items().length);
  readonly totale  = computed(() =>
    this._items().reduce((s, i) => s + i.prezzo * i.qta, 0)
  );

  // === Azioni ===
  aggiungi(prodotto: Prodotto, qta = 1): void {
    this._items.update(arr => {
      const esistente = arr.find(i => i.prodottoId === prodotto.id);
      if (esistente) {
        return arr.map(i => i === esistente ? { ...i, qta: i.qta + qta } : i);
      }
      return [...arr, { prodottoId: prodotto.id, prezzo: prodotto.prezzo, qta }];
    });
  }

  rimuovi(id: number): void {
    this._items.update(arr => arr.filter(i => i.prodottoId !== id));
  }

  svuota(): void { this._items.set([]); }
}

26.3 NgRx Signal Store

Da Angular 17 è arrivata la libreria @ngrx/signals: una sintassi minimal per store di stato basati su signal, con feature componibili.

typescript
import { signalStore, withState, withMethods, withComputed, patchState } from '@ngrx/signals';
import { computed } from '@angular/core';

export const CarrelloStore = signalStore(
  { providedIn: 'root' },
  withState({ items: [] as Item[] }),
  withComputed(({ items }) => ({
    count:  computed(() => items().length),
    totale: computed(() => items().reduce((s, i) => s + i.prezzo * i.qta, 0))
  })),
  withMethods(store => ({
    aggiungi(p: Prodotto) {
      patchState(store, ({ items }) => ({ items: [...items, { ... }] }));
    }
  }))
);

26.4 NgRx classico (Redux pattern)

Per app enterprise complesse — auditing, undo/redo, time-travel — NgRx classico ha ancora il suo posto. Il flusso è:

UI → dispatch(action) → reducer(state, action) → new state → UI

+ side-effect via "Effects" (chiamate HTTP innescate da action).

NgRx tradizionale ha molto boilerplate (action, reducer, effect, selector per ogni feature). È giustificato solo per app davvero grandi e team strutturati. Per il resto, Signal Store o servizi con signal sono migliori.
  • Parti dal più semplice: servizio con signal
  • Per stato strutturato, NgRx Signal Store
  • NgRx classico solo se serve veramente (audit, time-travel)
  • Pattern: signal privato + readonly pubblico + metodi che fanno update()

CAPITOLO 28SSR e Hydration

← Torna all'indice

SSR (Server-Side Rendering) significa generare l'HTML iniziale sul server. Vantaggi: SEO, performance percepita migliore, Core Web Vitals migliori. Da Angular 17, l'SSR è completamente integrato e la hydration funziona davvero bene.

28.1 Cos'è l'hydration

Senza hydration: il server invia HTML, il client lo butta via e ricostruisce tutto da capo. Spreco totale.
Con hydration: il server invia HTML, il client lo riusa e si limita a "rianimarlo" attaccando event handler e stato. Niente flicker, no rerender iniziale.

28.2 Abilitare SSR

terminal
# Su un progetto esistente
ng add @angular/ssr

# Su un progetto nuovo
ng new mia-app --ssr

Cosa cambia:

  • Aggiunge server.ts (server Express)
  • Aggiunge main.server.ts
  • Modifica app.config.server.ts
  • npm run build produce sia il bundle browser che quello server
  • npm run serve:ssr:mia-app avvia l'app con SSR

28.3 Hydration nel detail

typescript — app.config.ts
import { provideClientHydration, withEventReplay } from '@angular/platform-browser';

providers: [
  provideClientHydration(withEventReplay())
]

withEventReplay() registra gli eventi (click, keypress) avvenuti prima che JS sia caricato e li riapplica dopo l'hydration. Esperienza utente perfetta.

28.4 Codice browser-only

Sul server non hai window, document, localStorage, ecc. Devi proteggere il codice che li usa:

typescript
import { isPlatformBrowser } from '@angular/common';
import { PLATFORM_ID, inject } from '@angular/core';

export class MyService {
  private isBrowser = isPlatformBrowser(inject(PLATFORM_ID));

  salva(v: string) {
    if (this.isBrowser) {
      localStorage.setItem('k', v);
    }
  }
}

Oppure usa afterNextRender() che non viene eseguito su server:

typescript
constructor() {
  afterNextRender(() => {
    // qui sei garantito di essere nel browser
    const chart = new Chart(canvas, options);
  });
}

28.5 Static Site Generation (prerender)

Per pagine che non cambiano spesso (es. pagine marketing), Angular può pre-renderizzarle a build time:

terminal
ng build --prerender

Il build produce file .html statici per ogni route. Servili come HTML normale.

  • SSR genera HTML sul server, hydration lo riusa nel browser
  • ng add @angular/ssr aggiunge tutto il setup
  • provideClientHydration(withEventReplay()) per la hydration moderna
  • Proteggi il codice browser-only con isPlatformBrowser o afterNextRender
  • Per pagine statiche, usa --prerender

33.3 Configurazione del server (SPA fallback)

Le app Angular sono SPA: il routing è client-side. Se l'utente ricarica la pagina /users/5, il server non sa cos'è. Soluzione: tutte le route servono index.html.

nginx
server {
  listen 80;
  root /var/www/mia-app/browser;

  location / {
    try_files $uri $uri/ /index.html;
  }

  location ~* \.(js|css|svg|png|jpg|woff2)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
  }

  location = /index.html {
    add_header Cache-Control "no-cache";
  }
}
Non cachare mai index.html a lungo: gli utenti rimarrebbero bloccati su una vecchia versione anche dopo un nuovo deploy. JS/CSS hanno hash nel nome quindi possono essere cachati 1 anno.

CAPITOLO 34Pattern e anti-pattern

← Torna all'indice

Questa è una raccolta di indicazioni nate dall'esperienza. Non sono regole d'oro — sono indicazioni che ti faranno scrivere meglio il 90% delle volte.

34.1 Pattern raccomandati

1. Smart vs Dumb components

Distingui i componenti "contenitore" (che orchestrano, iniettano servizi, gestiscono lo stato) dai componenti "presentazionali" (che ricevono solo input e emettono output, niente DI). I dumb sono testabili e riusabili al 100%.

2. Single source of truth

Lo stato di una entità vive in un solo posto. Niente "ho il count nel componente, ma anche nel servizio". Confusione assicurata.

3. Inputs come dati derivati read-only

Un componente non dovrebbe modificare i suoi input. Se devi farlo, emetti un output e fai cambiare il padre.

4. Mai logica nel template

Niente espressioni complesse nei template: spostale in computed() o metodi. Il template deve leggere "ovvio".

html — male
<p>{{ users.filter(u => u.attivo && u.eta > 18).length > 0 ? 'Sì' : 'No' }}</p>
typescript + html — bene
readonly haAdulti = computed(() => this.users().some(u => u.attivo && u.eta > 18));

<p>{{ haAdulti() ? 'Sì' : 'No' }}</p>

5. Subscribe gestite o eliminate

Se ti subscrivi manualmente, usa takeUntilDestroyed(). Meglio ancora: non subscriverti, usa async pipe o toSignal.

6. Tipi forti ovunque

Niente any. Niente unknown "dimenticato". Le API rispondono HttpClient.get<User[]>, non get.

7. Lazy loading per default

Ogni feature è un chunk separato. Bundle iniziale piccolo, navigazione veloce dopo.

8. OnPush + Signal

Già detto, ma vale la pena ripetere: per i componenti nuovi, parti da qui.

34.2 Anti-pattern da evitare

❌ Logica HTTP nei componenti

Le chiamate HTTP vanno nei servizi. Il componente le orchestra.

❌ Stato in localStorage letto nei getter

Ogni accesso al getter rilegge lo storage. Carica una volta in un signal.

❌ Accesso al DOM con document.querySelector

Usa @ViewChild o viewChild(). Senza saltare le astrazioni di Angular.

❌ effect() per derivare valori

Già detto: usa computed(). Gli effect sono per side-effect veri.

❌ Subscribe annidate

"Callback hell" reactive. Usa switchMap/mergeMap.

typescript — male
this.svc.getUser(id).subscribe(u => {
  this.svc.getOrders(u.id).subscribe(o => {
    this.svc.getDetails(o[0].id).subscribe(d => { ... });
  });
});
typescript — bene
this.svc.getUser(id).pipe(
  switchMap(u => this.svc.getOrders(u.id)),
  switchMap(o => this.svc.getDetails(o[0].id))
).subscribe(d => { ... });

❌ Magic strings nelle route

this.router.navigate(['/users', id]) sparso in 30 file. Domani vuoi rinominare la route e impazzisci. Centralizza i path in costanti o crea una funzione factory.

❌ Componenti monstro da 800 righe

Se un componente supera le 200 righe è un segnale: probabilmente fa troppo. Estrai sotto-componenti, sotto-servizi, custom hook (signal-based).

  • Smart/Dumb components: separazione di responsabilità
  • Niente logica nel template, niente subscribe annidate
  • Tipizzazione forte: il TS è il tuo migliore amico
  • OnPush + Signal di default per i nuovi componenti
  • Componenti piccoli, focalizzati, testabili
